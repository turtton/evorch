# Agent instruction design

モデルが判断できる一般的な解法は委ね、実装だけでは伝わらない情報を短く伝える。
短さ自体を目的にせず、成果の質と制約の正しい理解を保つ。

## 編集の判断

- 先に実装・schema・プロンプトの合成箇所を確認し、どの情報が誰に届くかを把握する。
- 必要な成果物・応答、非自明な制約、操作の作用を残す。一般論、schema の言い換え、例、過去の失敗への注意書きは、判断を変える根拠がなければ除く。
- 契約は適切な責務の箇所で管理する。他ロールの説明を振る舞い指示へ転載しない。ただし、親の委譲判断と子の応答など、別の判断に必要な情報は双方に残す。
- 同じ受け手に同じ内容を重ねない。Orchestrator にはロールのプリセット・keyTriggers・delegate の説明が同じ system prompt / tools で届く。ロールの起用条件は keyTriggers、委譲先の仕様（渡すもの・返すもの・制約）は delegate の説明、Orchestrator 自身の行動はプリセットに置く。受け手が別の子ロールのプリセットは重複に数えない。
- 望む応答を直接指定する。実行できない要求には、その制約と可能な成果を応答させる。「繰り返すな」などの注意だけで済ませない。
- ツール説明は用途と、schema から分からない副作用・結果・制約を伝える。引数の意味は schema 側で管理する。
- 条件付きの詳細は、発見可能な reference・skill・適切なツールへ置き、必要なときに取得できるようにする。
- 権限、情報の出所、ユーザー意図の境界はコードで担保する。モデルの判断に必要な境界の説明は残し、文章だけで強制できるとは扱わない。

## 検証

変更が対象 agent に届くことを確認する。合成した system prompt で、同じ条件が重複していないことも確かめる。判断やツール選択を変える編集は、代表的な依頼で変更前後を比較する。
主モデルと fallback モデルについて、成功、誤ったツール呼び出し、未完了、制約の誤報告、総トークン数・cache 利用を変更の影響に応じて評価する。
静的テストは組み込みや契約の確認に使い、モデルの遵守を証明したとは扱わない。未評価の項目は明記する。

evorch の通常ターンでは、送信済みの system・tools の内容と順序、入力 prefix を改変しない。
cache に影響する変更では、既存の境界と `scripts/check-cache-contracts.sh` の契約を保つ。
