# ADR 0039: ツールを呼べる JS 実行環境（code mode）

## Status

Proposed（2026-10-22、下書き）。利用者との相談で、目的と方向（JS のみ、npm 不要、計測してから採否を決める）に合意した。この ADR で決めるのは設計の方針である。採否は「評価」の節の手順で決める。

2026-10-22 追記: 次の 3 つを加えた。コードに返す結果の形、エージェントへの説明、ターン数とトークン効率の検証。

2026-10-28 追記: 利用者との相談で、検証の方式を変えた。まず `run_js` ありで 5 つのモデルの使い方を Worker で観察し、改善の余地がある間は改善を続ける。`run_js` なしとの比較は、ありの費用を見てから行うか決める。あわせて、shell の複雑なワンライナーの進捗が分かりにくいという観点と、`run_js` の中の長い処理の見え方を加えた。

2026-10-29 追記（試作のその後の変更を受けた更新）: 試作（PR #397、`feat/run-js-prototype`、head `f139cccb`）と評価（課題 v1〜v3、ラウンド r1〜r4）で変わった点を反映した。子の呼び出しの上限と計上、子の結果の形、結果の本文の構成、打ち切られた子 shell の扱い、未観測の shell ジョブの一般的なガード、headless の終了コード、説明の要点、評価の経過、ワンライナーの数え方である。

## Context

oh-my-pi（`omp`）と senpi は、agent が JS や Python のコードを実行する `eval` ツールを持つ。コードの中から agent 自身のツールを呼べる。

- oh-my-pi は、状態を保持する Python と JS（常駐の Bun worker）のセルを持ち、セルの中から `tool.read` などを呼べる。`agent()` / `workpool` でサブエージェントも起動できる。JS 側は Bun/Node のファイル・プロセス・ネットワーク API をすべて使え、ドキュメント自身が sandbox ではないとしている（github.com/can1357/oh-my-pi の `docs/python-repl.md`）。
- senpi は拡張 `senpi-codemode` で、JS / Python / Ruby / Julia の状態を保持するカーネルを持つ。セル内の `wait()` / `handle()` を足すために、打ち切り・再接続・期限の扱いを含む大きな実装になっている（github.com/code-yeongyu/senpi PR #2687）。
- 同じ考え方は Cloudflare の Code Mode（blog.cloudflare.com/code-mode/）と Anthropic の "Code execution with MCP"（anthropic.com/engineering/code-execution-with-mcp）にもある。ツールをコードの API として渡し、中間結果をコンテキストに戻さずに処理させる。Cloudflare はコードを、渡したツールにしか触れない sandbox で動かす。

### 計測（2026-10-22、GUI の store から）

GUI の store を読み取り専用で集計した。対象は Tool イベントの 34,464 件（2026-09-09〜10-22、950 run）と、`usage_requests` の成功した 35,967 リクエスト（$842）である。ターンへの割り当ては「ツールの開始時刻より前にある、その run の最後のリクエスト」とした。読み取り専用かどうかは、ツール名と shell コマンドの正規表現で判定した。どちらも近似である。

ターンとトークンについて:

- ツールを使ったターンの 83%（20,775 / 25,071）は、1 ターンにつき 1 回の呼び出しだった。
- ツールを使ったターンの 38% は、読み取り専用のツールだけのターンだった。
- 読み取り専用のターンは 2 回以上続くことが多い。そのような区間は 1,434 あり、10 ターン以上の区間が 151、最長は 94 ターンだった。
- 各区間を 1 ターンにまとめられた場合に減るリクエストは、上限で 5,543 件（全体の 15.4%）になる。その分のプロンプトトークンは全体の 20.8%、費用は $175 / $842 である。内容を読んでから次を決める探索もあるため、実際に減らせる量はこれより小さい。

shell の中で書かれたスクリプトについて:

- python は 339 回呼ばれた。そのうち 157 回は、この環境に python がないため `command not found` で失敗した。
- node スクリプト（`node -e` やヒアドキュメント）は 194 回で、コマンド長の中央値は 1,144 文字だった。perl は 135 回だった。
- 用途は、正規表現による置換・集計、JSON の加工、sqlite の読み取り、テストログの集計である。
- スクリプトがファイルを直接書き換えた呼び出しは、python で 82 回、node で 99 回あった。これらは `edit` / `write` を通らない。そのため diff が表示されず、編集後のフック（`crates/tools/src/post_edit.rs`）も働かない。
- python または node を含む unsandboxed の呼び出しは 140 回あった。そのうち 52 回は store（sqlite）の読み取りだった。残りの多くは、worktree が sandbox の mount の外にある、ホストの toolchain や gh の認証が要る、といったスクリプト以外の理由によるものだった。

利用者から見ると、shell の中の長いスクリプトは何をしているかが追いにくい。とくにファイルの書き換えは、結果の diff でしか分からない。

2026-10-28 時点で、利用者は次のことにも気づいている（集計はしていない）。shell で複数の手順を 1 回のコマンドにつないだワンライナーを実行し、いまどの手順まで進んだのかが分かりにくいことが目立つ。たとえば、ビルド、テスト、`sed` や `git grep` での確認を `;` や `&&` でつないだものである。

計測の後に、shell と編集のツールが変わった。shell の同期呼び出しの自動の yield と完了までの poll（#370、#377、ADR 0042）、1 回の呼び出しで複数か所を編集できる `edit`（#310）、`apply_patch`（#353）である。そのため、この節の数値は現在の挙動の基準値としては使えない。

### 前提となる既存の部品

- ツールは `ToolExecutor`（`crates/tools/src/executor.rs`）を通して実行する。引数の検証、承認、結果の正規化、`ToolStarted` / `ToolCompleted` イベント（`crates/event-bus/src/event.rs`）はここで行う。
- ロールごとのツールの許可は `RoleCapabilities`（`crates/agents/src/capability.rs`、ADR 0002）で決まる。
- shell は bwrap の中でだけ実行する（ADR 0021）。sandbox の外での実行は、呼び出しごとの審査を通す。
- 書き込みには、パスの境界（ADR 0033）と、編集後のフックが適用される。
- 同じターン内の `Shared` のツールは並行に実行される（`crates/runtime/src/agent_loop/tool_calls.rs`）。
- 中断した tool 呼び出しは再実行せず、結果不明として復元する（`crates/runtime/src/restore/recovery.rs`、ADR 0026 / 0027）。
- thread の再実行による評価がある（`crates/eval`、ADR 0036）。

## Decision

### `run_js` ツールを加える

- agent が書いた JS を実行し、その結果を返すツール `run_js` を加える。名前に `eval` を使わない。`crates/eval` と Evaluator ロールの「評価」と紛らわしいためである。
- 対応する言語は JS（ES2023 相当）だけにする。Python などの他の言語には対応しない。npm パッケージと Node / Bun の API は提供しない。
- 使えるのは ECMAScript 標準の組み込みである。文字列のメソッド、正規表現（名前付きグループ、後読み、`\p{…}`）、`JSON`、`Array` / `Map` / `Set` などが含まれる。
- 実際に rquickjs 0.14（QuickJS-NG）で動かして確かめた（試作）。
  - 存在する: `queueMicrotask`、`performance`、`atob` / `btoa`、`WeakRef`、`eval`、`Function`、`Set` の新しいメソッド、Iterator helpers、`Object.groupBy`、正規表現の `v` フラグなど。
  - 存在しない: `structuredClone`、`setTimeout`、`fetch`、`require`、`TextEncoder`、`URL`、`Intl`、`import()`。
  - QuickJS-NG は Intl を実装しない。`localeCompare` は NFC に正規化した後のコードポイント順で比較する。ロケールは無視される。
- 引数は、コード（`code`）と、任意の時間の上限（`timeout_ms`）とする。コードはトップレベルの `await` を使える async 関数の本体として実行する。`return` した値と、`console.log` / `print` の出力を返す。戻り値の文字列はそのまま返し、それ以外は JSON にする（「モデルには結果だけを返す」の節）。

### エンジンは QuickJS を、sandbox の中の別プロセスで動かす

- エンジンには QuickJS-NG（QuickJS のフォーク）を、Rust のバインディングの rquickjs を通して使う。rquickjs は、メモリの上限、スタックの上限、割り込みのハンドラを持つ（`AsyncRuntime::set_memory_limit` / `set_max_stack_size` / `set_interrupt_handler`）。ビルドも軽い。
- エンジンは evorch のプロセスの中では動かさない。evorch のバイナリを JS worker のモード（例: `evorch js-worker`）で起動し、bwrap の中で動かす。この worker は、shell とは別の専用の `MinimalSandbox` で動かす（試作で確定）。制約は次のとおりである。
  - 読み取り専用で見せるのは、実行ファイル、検証済みの ELF loader、`ld.so` で列挙したライブラリだけにする。ワークスペースを含むその他のファイルシステムは見せない。
  - `/tmp` は private な tmpfs、`/dev` を置き、`/proc` は自分の PID namespace のものにする。
  - ネットワークと IPC を共有しない（`--unshare-net` など）。capability はすべて落とす。
  - credential を渡さない。環境変数も渡さないが、`LD_LIBRARY_PATH` だけは転送する（dev ビルドの動的ライブラリの探索に必要なため）。
  - loader は、`/nix/store` または標準のシステムディレクトリにある、root 所有で書き込みできないものに限る。ライブラリの列挙自体も bwrap の中で、期限と出力の上限を付けて行う。
  - 評価環境は NixOS である。FHS / usr-merge の環境では実機で確かめていない。
- 別プロセスにするのは、QuickJS のメモリ安全性のバグを、モデルが書いたコードから突かれても、sandbox の外にある evorch 本体に届かないようにするためである。プロセスが落ちた場合は、その呼び出しを失敗として返す。
- QuickJS の `std` / `os` モジュールは組み込まない。モジュールの読み込み（`import`）も提供しない。

### 外の世界にはツールを通してだけ触れる

- worker は、`tools.<name>(args)` を呼ぶと、ツール呼び出しの要求を stdio 経由で evorch 本体に送る。本体はその要求を、通常のツール呼び出しと同じ `ToolExecutor` で実行する。ロールの許可、パスの境界、network guard、承認、secret の秘匿、編集後のフックが、そのまま適用される。
- `tools.<name>` は Promise を返す。結果の形は「コードに返す結果の形」の節で決める。`Promise.all` で並行に呼べる。並行の可否は、ツールの `ToolExecutionMode` に従う。`Shared` のツールは並走し、`edit` / `write` / `shell` は単独で実行し、順序は program の順にする。
- コードから呼べるツールは、次の 2 つの条件をどちらも満たすものだけにする。
  1. その run のロールに許可されている。
  2. コードからの呼び出しを許す一覧に入っている。第 1 段階の一覧は `read`、`grep`、`git_diff`、`edit`、`write`、`shell` とする。
- コードからは、承認や審査が必要になる呼び出しを行わない。shell の `sandbox_access` は `isolated` だけを受け付け、`network` / `unsandboxed` はエラーで返す。承認が必要と判定された呼び出しもエラーにする。エラーの本文で、通常のツール呼び出しとして直接行うよう案内する。
- 委譲、ユーザーへの質問、goal、todo、`present` などの meta 操作と、MCP のツールは、第 1 段階ではコードから呼べない。

### コードに返す結果の形

既存のツールの出力は、モデルが読むことを前提にしている。たとえば `read` は 300 行 / 16 KiB で打ち切り、本文の末尾に `[Output truncated … Continue with read(...)]` という案内を付ける（`crates/tools/src/tools/read.rs`）。コードがこの本文をそのまま扱うと、案内の文が処理対象に混ざる。そこで、コードに返す結果を次のように正規化する。

- 結果は `{ ok, text, truncated, next, detail }` の形にする。
  - `ok`: ツールのエラーで `false` になる。
  - `text`: 本文だけを入れる。モデル向けの案内の文は付けない。
  - `truncated` / `next`: 打ち切りの有無と、続きを取るための引数。`read` の `next_offset` / `next_byte_offset` などを、ツールごとに構造化する。
  - `detail`: ツールが添えるメタデータ。
- 正規化はツールごとの変換として、本体の側で行う。モデルに返す通常のツールの出力は変えない。
- 子の結果の本文は、モデルに返す通常のツールの出力と次の点で異なる。
  - `edit` / `write` / `git_diff` の `text` は要約にする（`edited <path> (+N −M)` など）。全文の diff は `detail.diff` に入れる。コードが `text` を出力して、コンテキストに diff が流れ込まないようにするためである。
  - 子の `shell` の出力は、1 MiB までは全文を JS に返す。これは runtime 専用の sidecar に持ち、イベントと GUI に出る出力は従来どおり bounded のままにする。NUL も保持する。1 MiB を超えたら `truncated: true` と `next = {tool: "read", path}` を返す。ディスクに退避した出力の読み戻しはしない。
- 補助の関数を 1 つ用意する。`readText(path)` は、`read` の続きを自動で読み進めて全文を返す。合計の上限（初期値 4 MiB）を超えたらエラーにする。各回の `read` は、通常の子の呼び出しとして記録する。
- 補助の関数を増やすのは、評価で必要が示されたときに限る。

### エージェントへの説明

`run_js` の説明は、一般的なツールより長くなる。使える API と結果の形を示す必要があるためである。毎回のリクエストに載るので、次の方針で分量を抑える。

- **API の型宣言は生成する。** その run で使えるツール（ロールの許可とコードからの呼び出しの一覧の積）について、各ツールの JSON schema から TypeScript の型宣言を生成し、説明に埋め込む。手で書かないのは、説明と実装を別々に変えないためである（ADR 0010 の 6）。ロールごとに内容が変わるので、プロンプトのキャッシュは run の構成ごとに効く。
- **説明の本文は短くする。** 本文に含めるのは次の 5 つだけとする。
  1. 使う場面と、使わない場面
  2. 出力または `return` したものだけがコンテキストに入ること
  3. 結果の形と、`Promise.all` での並行の呼び出し
  4. 使えない API（fs、require、fetch、timers、Intl）と、コードから行えない呼び出し（承認が必要なもの、`isolated` 以外の shell）
  5. 上限
- **長い例は組み込みの skill に分ける。** 説明に載せる例は短いもの 1 つとする。長い使い方の例は組み込みの skill にして、必要なときに `skill_load` で読ませる。たとえば、まとめ読みと要約、複数ファイルの同じ規則での編集、テストログの集計である。この組み込みの skill は、試作では提供していない（後続で扱う）。試作の説明には、まとめ読み、同じ編集の繰り返し、shell 1 回での集計の 3 つの例を載せた。固定費は下の見積りより大きくなるので、評価で測る。
- **他のツールとの使い分けを書く。** shell のガイダンスには、データの加工や複数か所の編集を shell の中のスクリプトで行わず、`run_js` を使うよう書く。`edit` のガイダンスにも、同じ編集を多くのファイルに行うときは、shell の `sed -i` のループではなく `run_js` と `tools.edit` を使うよう書く。
- **長い処理は `run_js` に入れない。** ビルドや長いテストのように時間のかかるコマンドは、`run_js` の中ではなく、通常の shell のジョブとして実行するよう書く。`run_js` は時間の上限を持ち、待っている間は 1 つのツールの呼び出しとして見えるためである。cargo などのビルドとテストは、説明の例にも入れない。コンパイラの出力をコードで処理したいときは、通常の shell でファイルに書き出し、`run_js` でそのファイルを読むよう書く。
- **説明の要点（試作で追加）。**
  - shell の `python3 - <<EOF`、`cat > script.py <<EOF`、`node -e`、`perl -i -pe`、`awk`、集計や読み取りのための `for` ループ、`xargs sed -i` の代わりに `run_js` を使う。
  - shell の薄いラッパーや、1 回の呼び出しで済む作業には使わない。
  - ファイル全体や長いコマンド出力をダンプせず、必要な行や数だけを出力する。
  - `truncated: true` は `text` が一部だということである。`next` があれば `readText(next.path)` で続きを読み、`next` が null なら範囲を絞って呼び直す。部分的な出力から数えたり、結論を出したりしない。

説明の本文の下書き（他のツールに合わせて英語）:

```text
Run JavaScript (ES2023, QuickJS) that calls your tools, and return only what you print or return.
Use it to batch several reads/searches, filter or aggregate their output, or apply the same edit
across many places. Do not use it for a single tool call.
- Tool results stay out of your context unless you print or return them, so print only the essentials.
- `tools.<name>(args)` returns Promise<{ok, text, truncated, next, detail}>; run independent calls with Promise.all.
  `readText(path)` returns a whole file.
- Edits go through tools.edit / tools.write so they show as diffs. There is no fs, require, fetch, timers or Intl.
- Calls needing approval or non-isolated shell fail here; make them as normal tool calls.
- Run builds and long tests as normal shell jobs, not here.
- Limits: 30 s (timeout_ms up to 300000), 64 MiB JS heap, 1000 tool calls (following a `next` once is free).
Available tools:
<generated TypeScript declarations for this run>
Example: const hits = (await tools.grep({pattern: "TODO", path: "crates"})).text.split("\n"); ...
```

説明の分量の見積もり: 本文が 250 トークン程度、型宣言がツール 1 つにつき 40〜80 トークン程度で、合計 600〜800 トークンになる。計測の期間の 1 リクエストあたりのプロンプトは平均 12.6 万トークン（入力とキャッシュの合計）なので、その 0.5〜0.6% にあたる。実際の値は評価で測る。

### コード内の呼び出しは子のツール呼び出しとして記録する

- コード内の呼び出しにも、それぞれ `call_id`（`<親の call_id>/<連番>`）を割り当てる。`ToolStarted` / `ToolCompleted` を発行し、親の `run_js` の呼び出しを指す任意の項目 `parent_call_id` を持たせる。旧形式のイベントでは、この項目は欠落する。
- OTel では、親の `run_js` の span の子として記録する。
- 重複呼び出しの検出（`IdenticalToolCalls`）、予算、escalation の計上は、コード内の呼び出しも数える。`IdenticalToolCalls` には子の呼び出しも入る。計上は本体側の記録で行い、子の出力が artifact に退避されても影響を受けない。
- 計上は、コストに応じて次のように調整する。大量のファイルを処理するプログラムを、止まったループと取り違えないためである（`crates/runtime/src/agent_loop/run_js_accounting.rs`）。
  - 子の `read` / `grep` / `git_diff` は、tool call の予算に 10 回で 1 回分として数える。`edit` / `write` / `shell` は 1 回ずつ数える。
  - host が返した `next` に一致するページの継続は、1 回だけ無料にする。引数が `offset` だけ同じでも、継続とは見なさない。
  - 同一プログラムの中で、すでに実行された `shell` / `write` / `edit` の後に同じファイルを読み直すことは、再読（`max_file_rereads`）に数えない。artifact の `read` も再読に数えない。
- 呼び出しの上限を超えた後の要求は、一定の件数で打ち切る。その間に返すエラーメッセージは、バイト数で制限する。

### モデルには結果だけを返す

- モデルに返すのは、`return` した値と、出力したテキストだけにする。子の呼び出しの生の出力は、コードが出力しない限りコンテキストに入れない。これがトークンを減らすための要点である。
- 戻り値は、文字列ならそのまま生のテキストで返し、JSON の文字列にはしない。それ以外の値は JSON にする。実機で観察したところ、JSON の文字列にすると `\n` がエスケープされて読みにくく、サイズも増えたためである。
- 本文の形は、（失敗または打ち切りがあれば先頭にその通知）、出力、`=> <戻り値>`、最終行の要約の順にする。最終行は `[run_js: N calls, M failed (…); wrote: …; may have changed: …; warnings: …]` とする。
- 副作用を見落とさないよう、この要約を必ず付ける。要約に含めるのは、子の呼び出しの数、失敗した呼び出し（短い理由を添える）、書き換えたファイルの一覧、編集後のフックの警告があったことである。警告の本文は含めない。失敗の理由と警告の発生は本体側で保持し、コードが出力しなくても必ず要約に入れる。
- 最終行の要約は bounded にする。各一覧に件数と 1 件の長さの上限を設け、全体で 4.6 KB 程度以下に収める。打ち切られた shell は優先して名指しする。
- 本文全体は、capture の上限（8 MiB、`crates/tools/src/output.rs`）に収まるようにする。収まらないときは、最終行の要約が残るよう、出力（印字したテキスト）を先に削る。それでも大きい場合は、既存のツール出力と同じ artifact への退避に従う。
- GUI は、`detail.run_js.layout` のバイトオフセットで本文を区分する。印字した出力や戻り値に `=> ` で始まる行があっても、構造と取り違えないためである。
- JS の例外は、セル内の行番号を付けたスタックトレースとして返す。

### GUI で処理の中身を見せる

- transcript のツールカード（`crates/gui/src/panes/transcript_tool.rs`）に、次のものを表示する。
  - シンタックスハイライトしたコード
  - 子の呼び出しの行。既存のツール表示を流用するので、`edit` は diff、`shell` はコマンドと出力として表示される。
  - 出力と戻り値、エラー
- 実行中は、子の呼び出しを開始した順に追加して表示する。
- 子の shell の途中の出力（`ShellJobOutput`）は、通常の shell と同じく、`run_js` のカードの中の子の行に流して表示する。`run_js` の中の shell が何をしているかを、終わるまで待たずに追えるようにするためである。

### 状態は保持しない（第 1 段階）

- 第 1 段階では、呼び出しのたびに新しい JS のコンテキストで実行する。呼び出しをまたいで値を残さない。
- 中断した `run_js` は、他のツールと同じく結果不明として復元し、再実行しない。完了した子の呼び出しは、イベントとして残る。
- run の間に状態を保持するセルは第 2 段階で検討する（Open questions）。

### 上限

- 時間の上限の既定は 30 秒、最大は 300 秒とする。子の呼び出しを待つ時間も含める。上限を超えたら、割り込みで JS を止め、実行中の子の呼び出しを取り消す。run の停止と取り消しも同じ経路で止める。
- メモリの上限は 64 MiB、子の呼び出しは 1 回の実行につき 1000 回まで（設定 `max_tool_calls` の既定。試作の初期値 200 から、評価で引き上げた）とする。回数は「子の呼び出しの上限」の計上の調整を適用した後の値である。超えた後の要求は、一定の件数で打ち切る。64 MiB は QuickJS のヒープの上限であり、プロセスの RSS の上限ではない。
- 時間切れと取り消しでは、開始済みの子を停止して回収する。子の shell の停止を確認してから、親の `run_js` を完了する。停止を確認できない場合は、run を止め、workspace と ownership を保持したままにする（fail-closed）。
- `run_js` に打ち切られた子の shell の副作用は、原則として未観測として扱う。例外は、`run_js` 自身が最終行の要約でその shell を名指しし、その行が最終的な本文に残ったことを、runtime 専用の receipt で確認できた seq のジョブだけである。これは観測済みとし、通常の shell の応答と同等に扱う。receipt はツールだけが設定でき、本文のテキストは信用しない。stopped / cancelled / panic / 出力処理のエラーでは receipt がないので、未観測のままになる。未観測のままで durable snapshot がない環境では、run は Error になる。
- 未観測の shell ジョブがあるまま応答を終えたときの reminder は、`run_js` に限らない一般的なガードにする。reminder にはジョブの ID と状態を含める。連続 3 回、累計 10 回で run を Error にする。連続回数をリセットするのは、名指ししたジョブが解消されたとき（読み取り、停止、確認）だけで、他のツール呼び出しではリセットしない。きっかけは評価での暴走である。`run_js` の中の cargo が打ち切られて未観測のジョブが残り、モデルが同じ nudge に 483 回応答し続けた（料金表換算 $12.6）。
- いずれの値も初期値であり、評価の結果を見て調整する。

### 提供する範囲と既定値

- 付与できるロールの上限は、`run_js` を capability に持つロールである。Worker と、読み取りのロール（Explorer、Reviewer、Advisor、Planner、WebResearcher）がこれにあたる。コードから呼べるツールは、そのロールに許可されたものに限られる（`crates/agents/src/role.rs`）。そのため、読み取りのロールでは読み取りだけになる。
- Orchestrator には付与しない（ADR 0002）。Evaluator と MultimodalLooker にも付与しない。設定の `scopes` に書いても出ない。
- 設定で有効にしたときだけ付与する。既定は無効とし、評価の結果で既定を見直す。
- 有効にしても、出す先は `[tools.run_js] scopes` で絞る（user 層のみ）。要素は `"<role>"`（そのロールの全カテゴリとカテゴリ無し）か `"<role>:<category>"` で、表記は `agents.<role>` と `agents.<role>.categories.<name>` に合わせる。不正な要素は strict 検証でエラーにする。既定は `["worker:deep", "worker:high-reasoning"]` である。
  - 理由: 評価で luna（Explorer / WebResearcher / quick の担当）は `run_js` ありで悪化した。読み取りのロールは `run_js` の中から shell を呼べず利点が小さく、評価もしていない。high-reasoning の sol も未評価である。使いこなせるのは賢いモデルだけと判断し、当面は Worker の deep と high-reasoning だけに出す。
  - 判定は run の開始時に、ロールとカテゴリで行い、run の間は変わらない（プロンプトキャッシュ）。呼び出し時のゲートは、同じ判定を現在の設定で行い、さらにその run が開始時に `run_js` を持っていたことを要求する。無効化や scope からの除外は実行中の run の呼び出しも拒否し、追加した scope は次の run から効く。
  - 評価の headless 実行（`evorch run --role worker`）はカテゴリ無しなので、評価の overlay で `scopes = ["worker"]` を指定する（`evals/run-js/README.md`）。GUI の Agent features からも scopes を編集できる。
- 説明の内容は「エージェントへの説明」の節で決める。

### 評価

このツールの目的は、ターン数とトークンの効率を上げることである。あわせて、shell の中のスクリプトやワンライナーでしていた処理を、利用者が追える形にすることも狙う。評価は 2 段階で行う。

#### 第 1 段階: `run_js` ありで複数のモデルの使い方を観察し、改善する

- **方式**: Worker の run を、`run_js` を有効にして headless で実行する（`evorch run --role worker --prompt … --user-config <dir>`）。モデルは、モデルごとの設定ディレクトリ（overlay）で切り替える。ADR 0036 の thread の再実行は使わない。決めた課題を、モデルごとに同じ条件で走らせて観察するほうが軽いためである。
- **対象のモデル**: 5 つを候補とした。
  - provider `codex-personal`（Codex のサブスクリプション）: sol（`gpt-6.1-sol`）、luna（`gpt-6-luna+fast`）、astra（`gpt-6-astra`）
  - provider `claude-personal`（Claude のサブスクリプション）: opus（`claude-opus-5-5`）、sonnet（`claude-sonnet-5-5`）
  - 実際に評価したのは、sol を除く 4 モデルである。sol は provider が `model is not advertised` を返して使えず、利用者の判断で除外した。
- **headless の実行手順**（試作で確定）: 実行は `evorch run … --run-js-enabled <bool> --db <path>`、結果の確認は `evorch inspect --db <path> run <id> --full` と `events --run <id>` で行う。overlay は、`--user-config` が元の設定にフォールバックしないため、`config.toml` のコピーに `config.d` を重ねて作る。`config.d` で、候補が 1 件だけの評価専用の route を Worker に割り当てる（provider は固定）。headless の run は、blocking な質問で入力待ちになると、run を止めて終了コード 3 で終了する。入力待ちかどうかは、run の phase と永続化された質問の状態で判定する（`crates/evorch/src/headless.rs`）。答える人のいない質問で、評価の run が止まり続けないようにするためである。課題とスクリプトは `evals/run-js`（`feat/run-js-eval` ブランチ）にある。
- **題材**: evorch リポジトリの特定のコミットを使う。規模が大きく、まとめ読み・集計・複数か所の編集が自然に起きるためである。run ごとに、そのコミットから専用の clone か worktree を作る。利用者の作業ツリーでは実行しない。
- **課題**: 6 つ程度とする。課題ごとに、作業が正しく終わったかを確かめるコマンドを付ける。
  1. 複数のファイルにまたがる調査と要約
  2. ログや JSON の集計
  3. 複数か所を同じ規則で変える編集
  4. ビルドやテストを含む、複数の手順の作業
  5. 1 回のツール呼び出しで済む作業（`run_js` を使わないことが望ましい対照）
  6. 調査してから直す、混ざった作業
- **繰り返し**: まず各課題を 1 回ずつ走らせる予備の実行（5 モデル × 6 課題）で、手順と費用を確かめる。その後、ばらつきを見るため、各条件を 3 回程度に増やす。
- **観察する指標**: run ごとに次を集計する。
  - ターン数とトークン: リクエスト数、プロンプトトークン（入力、キャッシュの読み取り、キャッシュの書き込みを分ける）、出力トークン、費用
  - `run_js` の使い方: 使った回数、1 回あたりの子の呼び出しの数、コンテキストに戻した出力の大きさ、エラーと再試行、上限での停止、承認が必要な呼び出しを中で試みた回数
  - 使い分け: `run_js` が向かない場面（対照の課題、長いビルド）で使ったか、向く場面で使わなかったか
  - shell の中の処理: ヒアドキュメントのスクリプトの数、スクリプトによるファイルの書き換えの数、ワンライナーの複雑さ（1 回の shell の呼び出しにつないだ手順の数（`;` / `&&` / `||` / パイプで区切った数）とコマンドの長さ）、長いビルドと他の手順を 1 回にまとめた呼び出しの数
  - 品質: 確かめるコマンドの結果と、LLM による採点
- **改善の進め方**: 観察で見つかった問題（使うべき場面で使わない、誤った使い方、説明の誤解、結果の形の扱いにくさ）に合わせて、説明・結果の形・補助の関数・上限を直し、同じ課題で走らせ直す。改善の余地がある間は、費用をかけて繰り返す。直した内容と、それによる指標の変化を記録する。
- **集計の手段**: 上の指標を run ごとに出す集計を用意する。`evorch inspect` のサブコマンドか、store を読み取り専用で読むスクリプトとする（Open questions）。試作では、`evals/run-js/scripts/metrics.mjs` と `classify-shell.mjs` で集計している。
- **評価の経過**（2026-10-29 時点）:
  - 課題は v1 → v2 → v3 と改めた（`evals/run-js`、`feat/run-js-eval`）。v1・v2 は、モデルが集計や改名を 1 本のスクリプトで片づけ、往復が増えなかった。そのため `run_js` の効果を測れる規模にならなかった。v3 は、入力の種類、読まないと分からない項目、コンパイラの出力に従う手直し、複数 crate にまたがる変更を加え、往復が増えざるをえない形にした。
  - ラウンドは r1（予備、v1）、r2（v2）、r3（v3）、r4（v3、`f139cccb`）と進めた。r3 で、`run_js` の中の cargo の打ち切りから未観測のジョブが残る暴走が出た（「上限」の節）。r3 までの結果を受けて、計上、結果の形、説明、未観測のジョブの扱いを直した。
  - r4（v3、`f139cccb`、1 回目）: 24 組（4 モデル × 6 課題）が完走し、22 / 24 が合格した。料金表換算は $9.76 だった。`run_js` を使った課題数は、t5（対照）を除く 5 課題のうち、astra 5、luna 5、opus 3、sonnet 3 だった。Claude の 2 モデルは、説明を変えても、shell でプログラム（ヒアドキュメントなど）を書き続ける傾向があった。
  - r4 と同じ条件（v3、`f139cccb`）で、3 回の繰り返しを終えた。全 72 run が完走し、aborted などは 0 だった。結果は「評価の結果」にまとめた。

#### 第 2 段階: `run_js` なしとの比較

- 第 1 段階の費用を見てから、行うかどうかを決める、としていた。利用者の判断で行った。
- 第 1 段階と同じ課題・モデル・繰り返しで `run_js` を無効にして走らせ、指標を比べた（72 run、ラウンド r5）。第 1 段階だけでは、ターン数とトークンが減ったかは分からない。比べる相手がないためである。
- 計測の節の数値は、#370 / #377 / #310 / #353 の前の挙動なので、比べる相手には使わなかった。

#### 評価の結果

条件は、実装 `f139cccb`、v3 の課題 6 種、4 モデル（`gpt-6-luna+fast`、`gpt-6-astra`、`claude-opus-5-5`、`claude-sonnet-5-5`）、effort high、各 3 回である。`run_js` あり（ON）と なし（OFF）を 72 run ずつ走らせた。集計は `evals/run-js/results/r4-20261029/aggregate.md`（ON）と `results/r5-nojs-20261029/compare.md`（比較）にある（`feat/run-js-eval`）。

  - astra: prog は 0.05、script は 52 → 0 になった。一方で費用は 1.25 倍で、全体の増分の大半を占める。
  - luna: script は 34 → 9 になった。t1・t2 では、リクエスト数と時間が悪化した。
  - Claude の 2 モデルは部分的にしか移らなかった（script は opus 35 → 22、sonnet 62 → 35）。費用比は 1.02〜1.06 だった。

- 説明の固定費: `run_js` の定義により、最初のリクエストの入力が Claude で約 +2.25K、GPT で約 +1.4K トークン増える。この分は全リクエストに乗る。
- `run_js` の使われ方: 228 回で、コードの長さは中央値 836 字、p90 は 4,274 字だった。コードが長く、不透明さの一部が JS に移ったとの見方もある。ただし、子の呼び出しは 1 件ずつ記録され（計 8,038 件）、GUI のカードで追える。進捗の見えやすさは改善した。
- ON のみで出た副作用: reminder が 4 回、打ち切りが 2 回、`run_js` の中の cargo が 4 回（暴走はなし）。
- 費用: 観察したラウンド全体の合計は、料金表換算で約 $82 だった。実際の請求はサブスクリプションの枠である。

判断:

- ターン数とトークンの効率を上げる、という目的は支持されない。リクエスト数・費用・時間は ON のほうが大きく、新規入力は同等だった。
- shell のスクリプト的な実行（ヒアドキュメント、インラインスクリプト、長大なコマンド）の置き換えには、明確に効いた。とくに GPT 系である。品質の差は見られなかった。
- 「既定で有効にする条件」の「リクエスト数が増えない」を満たさないため、既定は無効のままにする。

#### 既定で有効にする条件

- 第 2 段階の比較で、次のすべてを満たすこととする。第 2 段階を行うまでは、既定は無効のままにする。
  - 品質（確かめるコマンドと採点）が下がらない。
  - 題材の集合で、作業あたりのプロンプトトークンが 10% 以上減る。
  - リクエスト数が増えない。
  - `run_js` が役に立たないはずの課題で、トークンの増加が説明の固定費の範囲に収まる。
- **導入後の確認**: 既定で有効にした後も、同じ集計で本番の thread を定期的に確かめる。集計するのは、ターンあたりの呼び出し数、読み取りの連続、作業あたりのトークン、`run_js` の使用率、ワンライナーの複雑さである。効果が薄れたり、説明の固定費が上回ったりしたら、説明か既定値を見直す。

## Alternatives considered

- **oh-my-pi / senpi と同じ、外部の JS ランタイム（Bun / Node / Deno）の常駐プロセス**: 採らない。ファイル・プロセス・ネットワークの API がそのまま使えるため、ツールの許可、パスの境界、審査を通らない経路が増える。bwrap の中で動かしても、shell との違いはツールを呼べる点だけになる。外部ランタイムへの依存も増える。
- **evorch のプロセス内で QuickJS を動かす**: 採らない。実装は簡単で速いが、エンジンのバグの影響が sandbox の外に及ぶ。
- **V8（deno_core）**: 採らない。ビルドの時間とバイナリの大きさに見合う利点がない。性能が必要になったら見直す。
- **boa（純 Rust の JS エンジン）**: 次点とする。メモリ安全性の面では有利だが、性能と成熟度で QuickJS に劣る。別プロセスの中で動かすなら、メモリ安全性の差は小さい。
- **Python の実行環境**: 採らない。利用者が確認しやすいことを重視し、言語を 1 つに絞る。
- **provider がホストする実行環境（Claude API の Programmatic Tool Calling など）**: 採らない。特定の provider でしか使えない。また、コードの実行がその provider の環境に移るため、evorch の sandbox と記録の外になる。
- **並列のツール呼び出しを促すだけ**: 補完の手段とする。1 ターンに 1 回の呼び出しが 83% なので、効果は見込める。ただし、集計や絞り込みで中間結果をコンテキストに入れずに済ませることはできない。

## Consequences

- 読み取りの連続をまとめ、中間結果をコンテキストに入れずに済むので、リクエスト数とトークンが減る見込みである。実際の効果は評価で確かめる。
- shell の中のスクリプトでしていた処理が `run_js` に移ると、ファイルの書き換えが `edit` / `write` を通るようになる。diff の表示と編集後のフックが効き、GUI で処理の中身を追えるようになる。
- rquickjs（C のコードを含む）が依存に加わる。JS worker のモードの起動と、stdio のプロトコルの保守が必要になる。
- `ToolStarted` / `ToolCompleted` に任意の `parent_call_id` が加わる。読む側（storage の投影、GUI、OTel、`crates/eval` の記録）は、子の呼び出しを扱えるようにする必要がある。
- コードからは承認の必要な操作ができない。そのため、権限の昇格が必要な作業では、従来どおり通常のツール呼び出しを使う。
- モデルが `run_js` を使いこなせるかは、モデルの系統によって差が出うる。そのため、評価の第 1 段階で Codex と Claude のモデルを観察する（候補は 5 つ、実際は 4 つ）。
- 評価は、利用者のサブスクリプションの利用枠を使う。評価の実行が、普段の作業の利用枠を減らす。
- `run_js` の説明は一般的なツールより長く、600〜800 トークン程度の固定費が毎回のリクエストにかかる。この固定費は、評価で効果と並べて測る。
- コード向けの結果の正規化は、ツールごとの変換として保守する必要がある。ツールの出力の形を変えるときは、変換も合わせて変える。

## Open questions

- 状態を保持するセル（run の間だけ値を残す）を第 2 段階で入れるか。入れる場合、停止・再開・compaction のときに状態が失われることを、モデルにどう伝えるか。
- コードから委譲（サブエージェントの起動と待機）を呼べるようにするか。ADR 0002 と ADR 0022 の境界との整合を検討する必要がある。
- MCP のツールを `tools.*` として呼べるようにするか。
- `web_fetch` などネットワークを使うツールを、コードから呼べる一覧に加えるか。
- `evorch inspect` に、この ADR の計測と同じ集計（ツール別の件数、読み取りの連続、shell の中のスクリプト）を出すサブコマンドを加えるか。今回は store を直接集計した。
- 時間・メモリ・呼び出し回数の上限の値。
- 組み込みの実測は、試作で rquickjs 0.14 を使って行った（「使えるのは ECMAScript 標準の組み込みである」の節）。文字列の操作と正規表現の細部は、評価で問題が出た場合に追加で確かめる。
- FHS / usr-merge の環境で、worker の `MinimalSandbox`（loader とライブラリの読み取り専用 mount）が動くか。評価環境の NixOS でしか確かめていない。
- ワンライナーの複雑さをどう数えるか。区切りの記号の数だけでは、引用符の中の記号や、パイプでつないだ 1 つの処理も数えてしまう。そこで、「プログラム的構造」を主指標にする案を採用し、評価の中で確かめている。
  - 数えるのは、ヒアドキュメントやインラインのインタプリタ本体、`for` / `while` / `xargs` によるファイルの反復、3 段以上の text 処理、複数のファイルへの `sed -i` である。
  - ファイルへの書き込みだけのヒアドキュメントは除く。
  - ビルドの連結数は別の指標とし、文字数は補助とする。
- 第 2 段階（`run_js` なしとの比較）は行った。結果は「評価の結果」の節にある。以降は、その結果を受けた検討事項である。
- `run_js` の位置づけ。既定は無効のまま維持し、効果を「スクリプト的な shell の置き換え」と「進捗の可視化」に置くか。
- 定義の固定費（1 リクエストあたり 1.4〜2.3K トークン）を減らせるか。
- luna で t1・t2 が悪化した原因の、個別の調査。
- `run_js` が想定する、大規模な走査や一括編集を含む課題での再評価。v3 の課題では、効果が出る規模に届いていない可能性がある。
- 既定で有効にするかどうか。保留する。
