# Default core-client (ADR 0045 PR08, default since stage 19a)

Run `evorch-gui [--config-dir /absolute/config]` beside the matching `evorch-core` binary: the core client is the default and needs no flag (`--core-client` is still accepted and changes nothing). Configuration identity uses `--config-dir`, then `EVORCH_CONFIG_DIR`, then the standard user configuration directory. The window never falls back on connection, launch or protocol errors: a core that cannot be reached or started is reported (in the window once it exists, otherwise as the process's error with exit 1). It has no runtime, storage or ownership of its own. The window is the same for GUI and CLI users of one configuration directory: both connect to, or start, the one core.

`evorch-core` is found only beside the running `evorch-gui` executable, as a regular executable (a symlink is refused). `cargo build -p gui` therefore does not run by itself: also build `evorch-core` (`cargo build -p gui -p evorch-core`). The Nix `evorch-gui-cef` package puts a wrapper for the store's `evorch-core` in its `libexec` directory, and the install check requires it.

The pre-single-core embedded runtime is removed. `--legacy-embedded`, `--demo`, `--state`, `--settings`, `--layout` and `--save-layout` are argument errors (exit 1, nothing opened); there is no way to start the window without a core. Data an existing user has is kept: the core reads the same `evorch-events.db` and `sidebar.json` of the configuration directory; `ui.toml` and saved layouts belonged to the embedded window and are not read.

The client-only window supports the host's projects and threads, paged committed history, lazy committed bodies (no token streaming), Worker/Orchestrator chat, queued follow-ups/withdrawal/next-turn delivery, Team objectives, continue/stop, routed questions and complete-input approval confirmation. New conversations use client-generated thread/submission IDs; host ingress determines Desktop/Human provenance. Files and clipboard images are locally read (8 MiB per file) and transferred in bounded base64 chunks with BeginAttachment/AppendAttachment/FinishAttachment to obtain validated project/thread-scoped attachment IDs. No client-local path is sent to or opened by the host. SendChat commits files to the core-managed persistent attachment root and sends only read-only paths in user text; images enter model history only if read opens them. Team-objective attachment inputs are explicitly Unsupported.

The snapshot is staged separately while a bounded 256-event/2 MiB buffer collects concurrent events. Only events after its high-water are applied; overflow, epoch changes and terminal subscription signals request a new cut. Revisions are equality tokens, not sort keys. Epoch replacement discards the old projection and invalidates attachment IDs, but retains text/image drafts and unknown-command state. Attachments can be explicitly reuploaded from retained bytes.

A lost command reply remains OutcomeUnknown. Reconnection uses the original receipt session and asks GetCommandReceipt; there is no unconditional retry. Unknown remains visible and retains its draft. Closing the window gives the client actor up to 500 ms to best-effort discard known unused attachment IDs, then aborts the actor/transport. It never sends StopRun/StopChat and does not own the core process. Reconnect is explicit after connection failure.

The optional existing-thread import requires its canonical project already approved by the current host. The host rechecks tombstones and project identity/trust, and uses ADR0024 claim/restore only for a Released, demonstrably offline foreign owner. Live and uncertain owners are not acquired. The window never reads the owners registry, run DB or legacy sidebar itself.

The execution, teams and lanes features (PR12) show, for the selected thread, its runs (roots, then the children of one run, with live/terminal/stopped/recovering and history-only told apart), goal and ledger, the team board and its tasks, and the lanes it leads (policy, detach, reattach, resume of held deliveries, and ending a managed lane by a person's decision). They read everything from the core with typed queries; an event only triggers a new read, so a late event never moves the screen back.

A person ends a managed (attached or summary) lane from its row: "人間の判断で閉じる…" records `human_closed` ("完了（未検証）"; no verification behind it) and "破棄する…" records `discarded`. Detached lanes offer neither. The confirmation reads the core's `GetLaneClosePreview` (the ledger's `lane_close_preview`, bounded; the client never opens the database) and shows whether a run of the lane is working, the number of unanswered questions, a missing Ready (when closing as done), and a Ready for an earlier brief as reference only, plus a required reason (at most 2 KiB). It states that nothing is stopped or deleted, that questions stay, and that a later Report lifts the close. Confirming sends `CloseLane` once with the revisions of the preview on screen (no double send). A refusal such as a stale revision is shown with its reason and nothing is resent: Reload reads a new preview, which becomes what is confirmed. A success or `AlreadyClosed` shows the kind of the record that stands; an unknown outcome (a disconnect) is never taken as a success, the lane is read again. The standing close is a badge ("close 済み: …") on the row and the detail, taken from `LaneSummary.current_close`; the host announces `LaneChanged` on a close, and a new Report lifts it the same way.

Management update operations of the old embedded window are available here, each through the core's typed commands and never by opening the database: in the sidebar (workspace feature) registering a project (name and directory; the core canonicalises the path and refuses one it does not accept), renaming it, approving or revoking its trust, and adding or removing its allowed directories, each sent with the revision of the access the core reported; in the settings feature adding and editing a provider (OpenAI-compatible, Kimi, Codex, Claude subscription, Cursor; the credential is an environment variable name or a keychain entry, never the key itself; other provider kinds are edited in the settings file), deleting one, saving the settings file, reloading models, and switching the Agent web tools of the running core (a runtime setting: its current value is not readable from the core and a restart returns it to the settings file's value). A refusal is shown with its reason; a lost reply is read back (or shown as unknown) and never sent again.

**Not available in this window yet:** changing a conversation's extra read directories (`SetThreadExtraReadDirs`): the sidebar shows the list read-only and says so. Features that have no screen are labelled in the "未対応の操作" panel (`Feature::unsupported`).

## Upload lifecycle and recovery

Enqueue synchronously registers a stable local draft ID, before the connection actor runs. Queued/in-flight/OutcomeUnknown images block send and discard; a full/closed queue keeps their bytes as unsent drafts for explicit retry. Only a known rejection or unsent failure makes an image retryable. Lost BeginAttachment/AppendAttachment/FinishAttachment replies retain the original request/session and draft ID. Applied AttachmentBegun/AttachmentAppended/AttachmentFinished receipts advance that draft; Unknown remains blocked across snapshot/epoch replacement, with no replay or reallocation. Explicit reconnect performs receipt reconciliation again, including when the previous receipt was Unknown.

Startup and upload reconciliation reclaim unfinished uploads only after proving creator death and acquiring their data-FD lock. Other live cores’ uploads remain reserved. Committed files have no upload TTL and remain available through restore/handoff until archive/delete.
